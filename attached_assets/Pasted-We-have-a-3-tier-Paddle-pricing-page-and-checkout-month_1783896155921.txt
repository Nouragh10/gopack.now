We have a 3-tier Paddle pricing page and checkout (monthly and annual plans). Build the fulfillment and provisioning layer in three parts, server-side only, against my Paddle live account.

## 1. Webhook handler with signature verification

Build a route handler that receives Paddle webhook deliveries, verifies the signature, and routes events to typed handlers.

- Verify the signature with the Paddle SDK before doing anything else. In Node this is `paddle.webhooks.unmarshal(rawBody, secret, signature)`.
- Pass the RAW request body to unmarshal (read it as text, e.g. `await request.text()` / `express.raw()`). Do NOT JSON.parse it first — a parsed body fails verification.
- Use the webhook notification SIGNING SECRET to verify, not the API key. They're different.
- If verification fails, don't return a 2xx. A 2xx tells Paddle the delivery succeeded and it stops retrying.
- Deliveries are at-least-once and can arrive out of order: make handlers idempotent (upsert keyed on the Paddle ID, don't blind-insert).
- Route verified events to handlers for subscription.created/updated/canceled, customer.created/updated, transaction.completed. Safely ignore other types.
- Create the live notification destination with the `paddle-live` MCP if available (otherwise tell me to create one under Developer tools > Notifications) and read back the signing secret. Store secrets in env vars; create/update `.env.example`.

## 2. Mirror subscription state and grant access

Mirror Paddle subscription and customer state into my database from verified events, plus a helper that decides whether a subscription currently grants paid access.

- Inspect my database first and match its existing conventions — use a database MCP if I have one connected (e.g. Supabase, or another Postgres/database MCP) to read my live schema directly; otherwise infer it from my data layer or ask me. If there are no tables, create `customers` and `subscriptions` (example below is Postgres — adapt to my DB).
- Access helper: treat `active` AND `trialing` as access-granting. Do NOT revoke access just because a `scheduled_change` to cancel or pause exists — only revoke when `status` is actually `canceled` (and handle `paused`/`past_due` per my rules).

    CREATE TABLE customers (
      customer_id TEXT PRIMARY KEY,
      email TEXT NOT NULL,
      created_at TIMESTAMP NOT NULL DEFAULT NOW(),
      updated_at TIMESTAMP NOT NULL DEFAULT NOW()
    );

    CREATE TABLE subscriptions (
      subscription_id TEXT PRIMARY KEY,
      customer_id TEXT NOT NULL REFERENCES customers(customer_id),
      status TEXT NOT NULL,
      price_id TEXT NOT NULL,
      product_id TEXT NOT NULL,
      scheduled_change_action TEXT,
      scheduled_change_at TIMESTAMP,
      created_at TIMESTAMP NOT NULL DEFAULT NOW(),
      updated_at TIMESTAMP NOT NULL DEFAULT NOW()
    );

## 3. Customer portal for self-service

Add an account screen that mints a Paddle customer portal session for the signed-in user and redirects to the returned URL. The portal is Paddle-hosted: customers update payment method, cancel, and view invoices there.

- Verify the user is authenticated FIRST. Resolve their Paddle customer ID server-side from the session — never trust a customer ID supplied by the client.
- Look up the customer (and subscription) in the tables above, then mint the session with the Paddle SDK. Read API key and environment from env vars.

## Guardrails — persistent entities you must NOT delete or offer to clean up

Some Paddle entities are part of the running system, not test litter. At no point — not now, not after testing, not when I say we're done — do you delete them or offer/suggest deleting them as "cleanup." Treat the following as permanent infrastructure:

- The webhook notification destination (and its signing secret) created in Part 1.
- Products and prices backing the 3-tier pricing page.
- Any customers, subscriptions, or transactions in Paddle or in my database — these are live state mirrored from real events, never disposable.

The events these entities drive — transaction.completed, subscription.created/updated/canceled, customer.created/updated — are the fulfillment path. Deleting their backing entities breaks fulfillment.

The one exception: a throwaway artifact YOU just created purely to test (e.g. a simulated event fired through the webhook simulator) that nothing above depends on — you may clean up ONLY that, and only after naming it and asking me first. It never covers the entities listed above, and if a step's completion depends on an entity, leave it. When in doubt, leave it and ask — never delete a Paddle entity or DB row to "tidy up."
